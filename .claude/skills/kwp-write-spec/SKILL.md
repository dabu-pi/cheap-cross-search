# kwp-write-spec（平山版・簡易仕様作成）

> **このSkillは平山独自開発ルールの下位テンプレートである。**
> `CLAUDE.md`、`CLAUDE_WORKFLOW_STANDARD.md`、
> Personal Skill `hirayama-workspace-repo-workflow`、
> および対象repo固有ルールが常に優先される。
> 本Skillの指示が上位ルールと矛盾する場合は、常に上位ルールを採る。

このSkillは、Anthropic公式 `knowledge-work-plugins` の `product-management/skills/write-spec`
を出発点に、平山ワークスペースの運用へ合わせて作り直した簡易仕様テンプレートである。
公式原本は `upstream-snapshot/94e1a08/` に改変なしで保管している。

外部Connector・MCP・OAuth・Slack・GitHub API・Notion・Datadog・Gmail 等は前提にしない。
これらが接続されていなくても、repo内の情報だけで完結させる。

---

## 目的

平山の短い依頼を受け取り、次を1本のドキュメントとして返す。

```text
短い依頼
→ repo・docs・testsの調査
→ 既存実装との整合確認
→ 実装可能な簡易仕様
→ 受入条件
→ 検証方法
→ 実装担当への引継ぎ
```

実際のアプリ機能実装は行わない。**仕様・受入条件・引継ぎまで**が本Skillの範囲である。

---

## 開始時に調べること（存在するものだけ）

対象repo内で次を探して読む。**無いファイルの新規作成を自動で要求しない。**

```text
CLAUDE.md
PROJECT_STATUS.md
NEXT_ACTIONS.md
RUN_LOG.md
HUMAN_NEXT_ACTIONS.md
README.md
package.json
tests / __tests__ / *.test.* / *.spec.*
既存仕様書（docs/ 配下の spec / design 等）
```

調査で確認できる内容は、質問として残さない。
コードとdocsを読めば分かることを平山に聞き返すのは、この運用の失敗である。

---

## 作業分類（最初に必ず決める）

依頼を次の3段階に分類し、以降の出力量をそれに合わせる。

| 分類 | 目安 | 出力方針 |
|---|---|---|
| 軽微 | 文言・定数・軽微なUI・明確なバグ修正。曖昧さ・回帰リスクが小さい | 長い仕様書を作らない。**短い実装メモ**にする |
| 通常 | 新規の小〜中機能。影響範囲が複数ファイルに及ぶが方針は明確 | 下記の全出力形式を簡潔に埋める |
| 高曖昧度・高リスク | 要件が曖昧／本番・DB・課金・認証・外部連携に影響／不可逆性がある | **実装計画を実行に移さず、承認点を明示して平山確認を要求する** |

過剰は害になる。実質的な曖昧さが無いのに重い仕様書を作らない。

---

## 守ること（平山ワークスペース固有の制約）

- 調査で確認可能な内容を質問として残さない。
- 実質的な曖昧さが無ければ、過剰な仕様書を作らない。軽微変更は短い実装メモにする。
- 高リスク変更は、実装開始前に平山確認を要求する。
- 未承認の本番変更を実装計画へ含めない。
- 複数repoを一括変更する計画を立てない。
- Vercel は **Protected Preview → owner visual確認 → main merge → Production** の順序を維持する。
  この順序を崩す計画を書かない。
- Supabase や本番DBへの変更を勝手に実行する計画を含めない。
- 見ていない画面の手順を書かない。不明な機能を実装済みとして扱わない。

---

## 出力形式

ALWAYS 次の見出し構成で出力する（軽微分類のときは各項を1〜2行に圧縮してよい）。

```text
1. 現状
   - repo・docs・testsの調査で分かった現在の実装・制約
2. 作業分類
   - 軽微 / 通常 / 高曖昧度・高リスク のいずれか＋判断根拠
3. 目的
   - この依頼で達成すること
4. 非目的
   - 今回やらないこと（スコープ外）＋各理由
5. 対象範囲
   - 変更する対象・変更しない対象
6. 影響ファイル候補
   - 調査で特定した変更が入りそうなファイル
7. UI／データ／ロジックへの影響
   - 画面・データ構造・処理ロジックそれぞれへの影響
8. 受入条件
   - Given/When/Then または チェックリスト形式。happy path・エラー・境界を含む
9. 検証方法
   - どう確認すれば受入条件を満たすと言えるか（typecheck/lint/test/build/手動 等）
10. リスク
    - 回帰・不可逆・本番影響・依存関係
11. 未解決事項
    - 調査で解消できず、平山または担当の判断が要る点（誰が答えるべきかを明記）
12. 実装担当への引継ぎ
    - 次の担当が着手できる粒度での実装計画・順序・承認点
```

高曖昧度・高リスク分類の場合は、11・12 に**承認点（何にYesが出れば着手できるか）**を明確に書き、
実装は開始しない。

---

## 出力のコツ

- スコープに対して意見を持つ。曖昧で広い仕様より、狭く定義された仕様の方が良い。
- 依頼が1本の仕様に対して大きすぎるなら、フェーズ分割を提案し第1フェーズだけを仕様化する。
- 非目的は目的と同じくらい重要。実装中のスコープ拡大を防ぐ。
- 未解決事項は本当に未解決なものだけ。調査で答えられる問いを混ぜない。
